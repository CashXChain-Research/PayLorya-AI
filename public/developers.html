Quickstart

  1. Create a key. In the dashboard, open Developers (left menu) and create an API key. Pick its scopes (read, write). Copy it right away: it is shown once.
  2. Make your first call. Check which account the key acts for:
export PAYLORYA_API_KEY=ply_sk_…

curl https://paylorya.valentin.is/api/v1/me \
  -H "Authorization: Bearer $PAYLORYA_API_KEY"

  1. Draft a payment. Find the payee, then draft. It waits for a person to approve it in the dashboard.
curl https://paylorya.valentin.is/api/v1/payees \

  -H "Authorization: Bearer $PAYLORYA_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: inv-2026-114" \
  -d '{"payeeId":"<payee id>","amountMinor":12000,"currency":"EUR","reason":"INV-2026-114"}'

Authentication

Send the key as a bearer token on every request:

Authorization: Bearer ply_sk_…
  • A key is ply_sk_ followed by 40 letters and digits. It acts for the account that created it, and sees only that account's data.
  • PayLorya AI stores only a SHA-256 hash of the key and a recognisable prefix (ply_sk_AbCd…WxYz). Lose the key and you create a new one.
  • Revoke a key under Developers; it stops working at once. An account holds up to 20 active keys.
  • An unknown, mistyped or revoked key gets 401 with "code": "invalid_key".
  • Call the API from your server or agent runtime, not from a browser page: the API sends no CORS headers, and the key would be exposed.

Scopes and human-only actions

ScopeAllows
readEvery GET: overview, forecast, payments, payees, budgets, transactions, documents, activity, chats, connections.
writeDrafting payments, uploading and deleting documents, starting and deleting chats, and messaging the AI CFO.

A call outside the key's scopes gets 403 insufficient_scope.

Human-only actions

Some actions move money, sign, or change credentials and the agent's rights. They stay with a person signed in to the dashboard. Any key, whatever its scopes, gets 403 human_only for:

  • approving, rejecting and signing payments;
  • connections (banks, wallets, CashXChain): adding, changing, refreshing, removing;
  • payees and budgets: adding, changing, removing;
  • the workspace and the agent's rights (autonomy, limits);
  • API keys and webhook endpoints: creating and removing;
  • requesting test tADA, linking CashXChain, and passwords.

Reading them is fine: a read key can list payees, budgets, connections, API keys (never the keys themselves) and webhook endpoints.

Payees count as rights. With full access the agent pays saved payees without asking, so a leaked key must not be able to add a payee or change its account details.

Drafting payments

POST /payments drafts a payment to a saved payee. A payment drafted with a key always waits for a person: its status is pending_approval, or blocked when it cannot execute as it stands (for example, no agent wallet or no connection with read & write access). policy.checks says why. Nothing is paid until someone approves it in the dashboard.

  "usdMinor": 12960,

  "reason": "INV-2026-114",
  "status": "pending_approval",

  "createdAt": "2026-10-31T09:25:40.019Z"

FieldRule
payeeIdA saved payee from GET /payees. Payees are added in the dashboard.
amountMinorPositive integer in the currency's minor unit: 12000 EUR is 120.00 EUR; ADA is in lovelace (1 tADA = 1000000); JPY has no minor unit.
currencyADA pays tADA on Cardano Preprod. USD, EUR, GBP, CHF, AED, PLN, SEK go to the CashXChain sandbox. JPY has no rail and is drafted as blocked.
reason1 to 300 characters, e.g. the invoice number.
documentIdOptional: links the payment to an uploaded document.

One payment per bill: a draft for the same payee and amount while one is still open, or for a document that already has an open or paid payment, is refused with 409 and creates nothing.

Statuses: pending_approval, blocked, approved, executing, awaiting_signature (a tADA payout waiting for the owner's wallet), executed, rejected, failed. Follow them with GET /payments or the payment.updated webhook.

Messages to the AI CFO (POST /chats/{id}/messages) are different: there the AI CFO acts as the agent, and the payments it drafts follow the account's agent autonomy and limits, set in the dashboard, exactly as in the dashboard chat.

Rate limits

  • Per key: 120 requests per minute, with bursts up to 120. Every authenticated request counts, including refused ones. Over the limit: 429 rate_limited and a retry-after header in seconds.
  • Per account and day: document uploads and messages to the AI CFO share a daily AI limit (150 by default), across the dashboard and the API. When it is reached: 429 without a code, until the next day (UTC).
HTTP/1.1 429 Too Many Requests
retry-after: 1

{ "error": "Too many requests with this key: try again in 1 s.", "code": "rate_limited" }

Idempotency

Send an Idempotency-Key header on every write (POST, DELETE), e.g. your invoice or job id. A retry after a timeout then never drafts a second payment.

  • Same key, same method, path and body: you get the first reply again, with the header idempotent-replayed: true.
  • Same key, different request: 422 idempotency_mismatch.
  • Same key while the first request is still running: 409 idempotency_in_progress. Retry shortly.
  • A first reply of 5xx is not kept: a retry with the same key runs again.
  • Keys are kept for 24 hours, separately for each API key. At most 200 characters.
  • A reply without a JSON body (204, the chat stream) is replayed as its status alone.

MCP for agents

Agents that speak the Model Context Protocol connect over Streamable HTTP with the same API key. What a key may not do over REST, it may not do over MCP: there is no tool to approve, sign or change payees.

Endpointhttps://paylorya.valentin.is/mcp
TransportStreamable HTTP
AuthOAuth sign-in (claude.ai, Claude Desktop), or Authorization: Bearer ply_sk_…

Claude (claude.ai and Claude Desktop)

  1. In Claude, open Settings → Connectors → Add custom connector.
  2. Paste https://paylorya.valentin.is/mcp and click Connect.
  3. Sign in to PayLorya AI and click Allow. Choose Read & draft (read, draft payments, ask the AI CFO) or Read only.

Claude finds the sign-in by itself (OAuth 2.1 with PKCE and dynamic client registration; metadata at /.well-known/oauth-protected-resource/mcp). Its token is an API key of your account named Claude (connector), listed under Developers in the dashboard: revoke it there to disconnect Claude.

Claude Code

claude mcp add --transport http paylorya https://paylorya.valentin.is/mcp \
  --header "Authorization: Bearer ply_sk_…"

Verifying the signature

x-paylorya-signature is t=<unix seconds>,v1=<hex>, where v1 is HMAC-SHA256 with your secret over <t>.<raw body>. Verify it against the raw body, before parsing:

import { createHmac, timingSafeEqual } from "node:crypto";
import express from "express";

const SECRET = process.env.PAYLORYA_WEBHOOK_SECRET; // whsec_…

/** True when the signature matches the raw body and is at most 5 minutes old. */
function verify(rawBody, header, secret, toleranceSec = 300) {
  const parts = Object.fromEntries(header.split(",").map(kv => kv.trim().split("=")));
  const t = Number(parts.t);
  if (!parts.v1 || !Number.isInteger(t) || Math.abs(Date.now() / 1000 - t) > toleranceSec) return false;
  const expected = createHmac("sha256", secret).update(`${parts.t}.${rawBody}`).digest();
  const given = Buffer.from(parts.v1, "hex");
  return given.length === expected.length && timingSafeEqual(given, expected);
}

const app = express();
app.post("/webhooks/paylorya", express.raw({ type: "application/json" }), (req, res) => {
  const raw = req.body.toString("utf8");
  if (!verify(raw, req.get("x-paylorya-signature") ?? "", SECRET)) return res.sendStatus(400);
  const event = JSON.parse(raw);
  if (event.type === "payment.updated") {
    const { payment, previousStatus } = event.data;
    console.log(`${payment.id}: ${previousStatus} -> ${payment.status}`);
  }
  res.sendStatus(204);
});
app.listen(3000);

Delivery

  • Answer with any 2xx within 10 seconds to acknowledge. Anything else (redirects are not followed), or no answer, is retried: 6 attempts in all, at once and then after 1 min, 5 min, 30 min, 2 h and 6 h.
  • GET /webhooks shows each endpoint's lastDeliveryAt and lastStatus (0: no HTTP answer).
  • Retries can deliver the same event more than once: deduplicate on the event id.
  • Answer quickly and do slow work afterwards.
